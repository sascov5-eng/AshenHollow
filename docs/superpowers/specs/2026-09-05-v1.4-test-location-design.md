# Ashen Hollow v1.4 — Perfected Test Location Design

Date: 2026-09-05
Status: Approved in chat, pending written-spec review
Baseline: device-approved v1.3 (`51ff84b21fa701150dbe386cc1be3c69565ee88e`)
Target release: v1.4

## 1. Goal

v1.4 is a developer-facing test location, not final story content and not final art. Its purpose is to put every currently relevant traversal, combat, hazard, checkpoint, interaction, secret, tutorial, and camera scenario into one coherent continuous location that can be repeatedly tested on a real iOS device.

The location must be easy to diagnose. Each mechanic is introduced clearly, tested in its own readable section, and accompanied by an explicit developer hint. The goal is not challenge or mystery; the goal is reliable verification.

## 2. Non-goals

v1.4 will not add final environment art, story progression, ability unlocks, resource-loss-on-death, secret rewards, complex moving-platform paths, complex enemy AI, final enemy art, or a final mixed-mechanics gauntlet.

The v1.3 camera behavior is preserved unless device testing of the new location reveals a concrete problem.

## 3. World structure

The entire test location is one large continuous physical world. There are no room loads, hard camera swaps, or teleports used to connect ordinary sections.

The architecture uses large cave spaces and natural height changes:

- broad horizontal traversal areas;
- open chambers;
- narrow connectors and tunnels;
- a tall vertical shaft;
- upper and lower routes;
- pits and drops;
- small optional side rooms;
- a shortcut that reconnects later space to an earlier area.

The main route is mostly linear so every required mechanic is encountered in a deterministic order. Small branches, loops, upper/lower alternatives, and secrets exist only where they help test exploration or a specific mechanic.

All critical mechanics must appear on the main route. Optional branches may contain only secrets or additional verification opportunities.

## 4. Approved route order

The main test flow is:

1. Start
2. Basic movement
3. Jumping
4. Checkpoint 1
5. Spikes and safe-position recovery
6. Horizontal moving platform
7. Vertical moving platform
8. Checkpoint 2
9. Ground patrol enemy
10. Flying enemy
11. Aggressive enemy
12. LIGHT gain and HEAL verification
13. Lever and normal door
14. Breakable secret wall
15. Hidden passage
16. Shortcut back toward an earlier area
17. Vertical shaft with wall slide / wall jump
18. Dash section
19. Long-jump section
20. Pit / death-zone test
21. Checkpoint 3
22. More demanding platforming
23. Small combat area containing two enemy types together
24. Narrow tunnels and elevation changes
25. Checkpoint 4
26. Final optional verification space
27. `TEST AREA COMPLETE` exit marker

There is no final combined obstacle gauntlet. Mechanics are intentionally separated so failures are attributable to a specific system.

## 5. Developer tutorial system

Every mechanic in the test location must have an explicit developer-facing hint. This is mandatory because the user is testing mechanics, not discovering them as a normal player.

Examples include:

- `MOVE`
- `JUMP`
- `DASH`
- `WALL JUMP`
- `ATTACK`
- `HEAL`
- `SPIKES`
- `PIT / DEATH ZONE`
- `MOVING PLATFORM`
- `CHECKPOINT — ACTIVATE`
- `LEVER`
- `DOOR`
- `SHORTCUT`
- `SECRET WALL`
- `HIDDEN PATH`
- enemy-type labels where useful
- `TEST AREA COMPLETE`

For input mechanics, the associated HUD button is highlighted or pulsed. For non-input mechanics, the relevant world object or hazard is highlighted enough to make the test target obvious.

A tutorial hint appears when entering its trigger zone. For input-driven actions, it disappears immediately after the first correct input is detected; successful completion of the obstacle is not required to dismiss the hint.

Completed tutorial hints stay completed across player death and respawn. They reset only on a full app/test-session restart.

## 6. Checkpoints

There are exactly four visible, interactive checkpoints.

Checkpoint placement is based on gameplay sections rather than equal map distance:

- Checkpoint 1: after basic movement and jumping introduction.
- Checkpoint 2: after spike recovery and moving-platform tests.
- Checkpoint 3: after the major traversal/interaction block and before the more demanding later platforming.
- Checkpoint 4: near the final verification section.

Activating a checkpoint:

- visually changes the checkpoint into an active state;
- makes it the current respawn point;
- restores player HP to full;
- preserves current LIGHT;
- does not respawn enemies;
- does not reset doors, shortcut state, breakable walls, or tutorial completion.

The player may always walk back through the level after reaching later checkpoints.

## 7. Death, pits, spikes, and safe recovery

### 7.1 Pit / void

Falling into a pit is a true death.

Pit detection uses both:

- a global bottom-of-world kill threshold; and
- explicit invisible local death zones for deep pits whose geometry may coexist with valid world space below or elsewhere.

On pit death:

1. player falls into the death condition;
2. a short 0.5–0.8 second visual fade occurs;
3. player respawns at the last activated checkpoint;
4. HP is restored to full;
5. all enemies respawn to their initial state;
6. player receives about 1 second of invulnerability after respawn;
7. no separate `YOU DIED` screen is shown.

The camera must not visibly travel back through the entire level. The reposition happens while the recovery transition obscures the world.

### 7.2 Spikes

Spikes are not an instant-death hazard.

On spike contact:

- player loses exactly 1 HP;
- a short 0.3–0.4 second flash/fade recovery transition occurs;
- controls are briefly locked;
- player returns to the most recent valid safe position;
- player receives about 1 second of invulnerability;
- if the spike damage reduces HP to zero, normal death/respawn rules apply instead.

### 7.3 Safe-position tracking

The safe-position tracker updates automatically only while the player is stably standing on normal safe ground or a safe platform.

It must not update while the player is:

- jumping;
- falling;
- dashing;
- wall sliding;
- touching or entering a hazard;
- in an unsafe edge state.

The saved point must have adequate collider clearance so the player cannot be restored partially inside geometry or directly into a hazard.

## 8. Player damage and invulnerability

A normal enemy hit:

- removes 1 HP;
- applies a short readable knockback;
- gives approximately 1 second of invulnerability frames;
- visually communicates i-frames by flashing/blinking the player.

Enemies must not be placed directly on top of checkpoints or in a way that causes unavoidable damage immediately after respawn.

After checkpoint respawn, the player also receives approximately 1 second of invulnerability.

## 9. LIGHT and healing

A successful player melee hit on an enemy grants `+34 LIGHT`.

LIGHT is capped at 100. Three successful hits therefore fill the meter from zero to 100.

HEAL behavior:

- requires 100 LIGHT;
- requires current HP below maximum;
- player holds HEAL for about 1.0 second;
- successful focus restores exactly 1 HP;
- successful heal consumes all 100 LIGHT;
- receiving damage while focusing cancels the heal;
- interrupted healing does not consume LIGHT.

Checkpoint activation restores HP but preserves LIGHT.

## 10. Test enemies

Enemies are functional developer placeholders, not final art or final production AI.

Three individual enemy types must appear in separate test sections before any mixed encounter:

### 10.1 Ground patrol enemy

A simple ground-based enemy that patrols a constrained area. Used to verify attack hitboxes, collision, player damage, knockback, enemy HP, enemy death, and LIGHT gain.

### 10.2 Flying enemy

A simple airborne enemy used to verify combat against targets above or away from the ground and to expose vertical hitbox/positioning problems.

### 10.3 Aggressive enemy

A simple enemy that notices the player and actively approaches/attacks. Used to verify aggro, contact/attack damage, knockback, and i-frames under pressure.

Later in the route, one small combat area contains two enemy types simultaneously. It is a verification encounter, not a high-difficulty combat challenge.

Enemy persistence rules:

- leaving an area and returning preserves surviving enemies' current HP/state;
- activating a checkpoint does not reset or respawn enemies;
- player death respawns all enemies to their initial state.

The existing Little Axion `Hurt` and `Death` animations must be connected to real player hurt/death states in this build.

## 11. Doors, levers, shortcut, and persistent world state

### 11.1 Normal lever and door

One normal lever opens one normal door.

The lever is one-shot for v1.4:

- activate lever;
- door opens;
- door remains open for the rest of the current test session;
- the lever does not toggle the door closed again.

### 11.2 Shortcut

The player sees the closed shortcut from the locked side before it is opened. A developer hint makes its function obvious.

Later, the player reaches the far side through the main route and activates a separate lever that permanently opens the shortcut for the current test session. The player can then use it to return toward earlier parts of the level.

This tests spatial continuity and persistent world state without introducing a room-loading system.

### 11.3 Persistence across death

The following states persist across player death:

- opened normal door;
- opened shortcut;
- destroyed breakable secret wall;
- completed tutorial hints.

They reset only when the app/test session is restarted.

## 12. Secrets

There are exactly two secret-mechanic demonstrations in the required test scope:

### 12.1 Breakable wall

The wall is intentionally discoverable in developer blockout. On approach, a `SECRET WALL` / `ATTACK` hint and corresponding highlight identify it. Hitting it with the intended attack opens the passage.

### 12.2 Hidden passage

A separate hidden path is visually hinted in the developer build. On approach, `HIDDEN PATH` and a subtle but unmistakable highlight identify the traversable area.

Behind each secret is only a small simple room. There are no rewards, currencies, collectibles, progression systems, or additional mechanics inside. The purpose is to test secret detection and access without overloading the test location.

## 13. Moving platforms

v1.4 contains exactly two basic moving-platform demonstrations:

- one horizontal back-and-forth platform;
- one vertical up-and-down platform.

Movement is constant, readable, and deterministic. There are no complex waypoint paths or trigger-driven moving-platform sequences in v1.4.

The player must ride both platforms without sliding off due to platform motion, visible jitter, or camera instability.

Each moving-platform section has a safe reachable embark point and safe reachable disembark point.

## 14. Traversal geometry and reachability invariants

No required platform or jump may be placed by eye alone.

The implemented test layout must be validated against the real player controller values used by the compiled build.

For every intended main-route transition, the implementation must know whether it is designed for:

- ordinary jump;
- running jump;
- jump + dash;
- wall jump;
- moving-platform transfer.

A transition that is presented as a normal jump must not secretly require dash. A dash test must be tuned specifically to jump+dash capability. A wall-jump shaft must allow clean alternating wall contact and a reachable exit.

Every required transition must satisfy all of the following:

1. the destination is reachable from the intended previous surface using the intended movement ability;
2. the player's collider and head trajectory have adequate clearance;
3. the player can land on the destination with a useful safety margin rather than a single-pixel edge case;
4. the route can continue onward from that destination;
5. ceilings, overhangs, and decorative collision do not invalidate the intended jump arc;
6. platform spacing remains valid after build-time source transformations are applied.

Automated validation must cover key distances, vertical clearances, and required route connectivity using the same tuning values as the gameplay code or a shared authoritative source of those values.

## 15. Camera

The device-approved v1.3 camera behavior is the baseline and is not intentionally retuned for v1.4.

The new location intentionally exercises the camera through:

- long horizontal traversal;
- broad open spaces;
- narrow tunnels;
- a tall vertical shaft;
- large downward movement;
- moving-platform travel;
- shortcut return traversal.

The level is designed around the existing camera. If real-device testing exposes a camera problem, that issue is handled as a separate targeted follow-up rather than silently changing v1.3 behavior during map construction.

Normal movement remains smooth, with camera dead-zone/look-ahead behavior preserved. Death and spike recovery may reposition camera while the screen is obscured by the recovery transition.

## 16. Visual style for v1.4

v1.4 uses a polished developer blockout rather than final environment art.

Gameplay categories must be visually distinct enough to diagnose at a glance:

- safe collision geometry;
- spikes;
- pit/death areas;
- moving platforms;
- doors;
- levers;
- checkpoints;
- breakable walls;
- hidden passage indicators;
- test enemies;
- tutorial trigger/target highlights where appropriate.

The blockout should feel spatially coherent, but final textures, decorative art, narrative props, final enemy visuals, and production VFX are outside v1.4 scope.

## 17. End of test location

The route ends at an obvious world-space exit/goal marker.

Approaching it shows:

`TEST AREA COMPLETE`

Reaching the end does not teleport the player, restart the level, end the app, or lock movement. The player remains free to turn around and traverse the entire test location again.

## 18. Release identity

The next assembled test build is v1.4.

Release contract:

- `CFBundleShortVersionString = 1.4`
- `CFBundleIdentifier = app.ashenhollow.prototype`
- `CFBundleVersion = 2`
- landscape left/right only
- preserve the working minimal package/signing structure from the device-proven build lineage
- preserve all nine Little Axion animation PNG resources in the app bundle
- top-of-screen developer label must include `v1.4` and a concise description specific to this build; proposed wording: `v1.4 • PERFECTED TEST LOCATION`

The top label remains visible so a device screenshot proves which exact mechanics build is installed.

## 19. Automated acceptance gates before IPA packaging

The CI build must fail before packaging if any required v1.4 contract is violated.

At minimum, automated checks must verify:

- v1.4 release metadata and developer label;
- required package identity remains unchanged;
- all nine Little Axion resources are present;
- four checkpoints exist;
- both moving-platform types exist;
- ground, flying, and aggressive enemy definitions/placements exist;
- spike hazards exist;
- global and explicit pit/death-zone handling exists;
- safe-position recovery exists;
- one normal lever/door pair exists;
- one shortcut lever/door pair exists;
- breakable-wall secret exists;
- hidden-passage secret exists;
- tutorial trigger coverage exists for every required mechanic;
- main-route geometry satisfies reachability and head-clearance invariants;
- checkpoint and safe-respawn positions are not inside hazards or collision;
- moving-platform embark/disembark points are reachable;
- required main route has no disconnected mandatory section;
- v1.3 camera constants/contract remain unchanged unless explicitly approved otherwise.

## 20. Real-device acceptance

CI success is necessary but not sufficient.

v1.4 is considered truly working only after installation on the user's real iOS device and manual verification of the location using the developer hints.

Manual device verification must cover at least:

- movement and jump section;
- spike damage and safe-position return;
- pit death and checkpoint respawn;
- all four checkpoints;
- both moving platforms;
- each enemy type individually;
- mixed two-enemy encounter;
- enemy respawn after death and persistence without death;
- LIGHT gain;
- successful HEAL;
- interrupted HEAL;
- player hurt/death animations;
- normal lever/door;
- shortcut opening and backtracking;
- breakable wall;
- hidden passage;
- wall slide/wall jump shaft;
- dash section;
- long-jump section;
- narrow-tunnel camera behavior;
- vertical camera behavior;
- end marker and unrestricted backtracking.

Only after the user confirms this device test should the perfected test location be treated as a stable baseline for building the final game world.

## 21. Implementation architecture guidance

The v1.4 implementation should not continue expanding one monolithic `GameScene.swift` or stack additional ad-hoc build-time string replacements for each gameplay subsystem.

The existing v1.2/v1.1/v1.3 build transforms are accepted historical constraints, but v1.4 should move new behavior into focused source units with clear responsibilities. Likely units include world/test-layout definition, hazard handling, checkpoint/respawn state, tutorials, moving platforms, enemy test logic, persistent test-session world state, and interaction objects.

Any refactor of the existing build-time transforms must preserve the device-approved v1.3 behavior exactly and be covered by contract tests before replacing the old path.

Implementation details and exact file breakdown belong in the subsequent implementation plan, not this design specification.
